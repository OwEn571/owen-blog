### Q3. 详细介绍一下多模态论文助手项目

我解释了一下简历版本可能还是 LangChain/LangGraph，但现在主要逻辑已经从 LangChain 里拿出来了，变成我自己写的 Agent Loop。

项目初衷有两个：一是提前练习非结构化 PDF 文档提取，因为后续比赛可能会涉及 PDF 解析；二是解决本地 Zotero 论文库检索不好用的问题。比如突然想到一个概念，Zotero 很难帮我跨论文找到来源或做比较。

实现上分成离线入库和在线查询。离线阶段，我会对每页 PDF 计算表格/图文分数，分数高的页单独标记；普通文本用 PDF 直接提取入库，复杂页面用 Unstructured 的 hi-res 模式提取 table、figure 等结构化块，形成文本块和图表块两层入库。在线检索时，如果召回到图表或表格内容，就调用多模态模型进一步解析。

Agent 编排上，我会先做意图拆解和 query rewrite，把 query 里的目标论文、问题类型、约束等信息写进结构化 state，再广泛召回论文和 evidence。不同问题模式走不同 solver，最后由大模型加工并流式返回前端。

> **AI**：项目介绍完整，尤其是"两层入库 + 多模态按需解析 + 结构化 state + solver"这条链路讲清楚了。小问题是内容太长，面试官听到后半段可能会抓不住重点。更好的口述结构是三段式：① 为什么做：Zotero 检索弱 + PDF 多模态信息难读；② 离线怎么做：文本/图表双通道入库；③ 在线怎么做：意图结构化、检索 evidence、solver 求解、流式返回。每段 20 秒。

### Q4. 为什么把 LangChain/LangGraph 替换掉？

我现在这个项目更偏 Plan and Execute。我会生成一个计划表，如果用 LangGraph 表达，就要在每个节点后面写 command 或条件边，让它回去再执行，逻辑会写得很长。但我自己直接写一个队列就实现了。

我并不是完全不用 LangChain。LangChain Core 里的 Document 类、Milvus 向量库封装、递归切块等组件还是在用，只是主架构没有再用 LangGraph 编排。

> **AI**：回答很好，比一面更准确。你这次明确区分了"不用 LangGraph 做主控"和"继续使用 LangChain 生态组件"，这很重要。核心判断是：LangGraph 适合流程预定义、状态边界清晰的 workflow；你的项目是动态计划队列，Plan 可能在执行中变化，用轻量 AgentRuntime 更自然。建议补一句："我不是为了造轮子，而是把 LangChain 用在适合它的组件层，把编排层收回来。"

### Q5. RAG 与工具调用是怎么规划的？

我先定义一些最小化工具，比如 search_corpus、read_memory 之类。工具有自己的 schema，Agent 只能看到工具名和参数定义。第一步意图识别时，会根据用户问题做一个初步 plan，把需要调用的工具名放入队列，然后逐个执行。

RAG 这部分更像项目底座，因为所有 solver 都依赖检索，所以不太需要额外规划"哪一轮用不用 RAG"。主要规划的是工具映射和调用顺序。

> **AI**：这道题回答略弱。面试官其实想问"怎么决定某轮用 RAG、某轮用工具、某轮用模型思考"，你回答成了"工具 schema 怎么定义"。更好的说法是：我的规划分两层。第一层是 Router/Planner 判断问题类型，决定 solver 和工具序列；第二层是每个 solver 内部固定调用 RAG 检索、证据抽取、校验等子步骤。也就是说，RAG 是求解器的默认证据来源，工具调用是按 plan 队列执行的可扩展动作。

### Q6. 有没有看过 Agent 或大模型应用方向的行业论文？怎么看 RAG、向量检索、文本检索的未来？

我当时说最近 Agent 论文看得不多，更多看工业代码，比如 Claude Code、OpenCode 这类。我观察到 coding agent 倾向把 bash 作为核心能力，而不是所有信息都走 RAG；动态文档可以通过 MCP 获取。我理解 RAG 不是落后，而是公司内部文档不能泄露到外部，所以必须用 RAG 做内部检索。

面试官进一步追问：不是因为不能泄露就用 RAG，而是不同检索方式在大模型上哪种更高效、哪种代表未来，是向量还是文本？

我回答：我的项目里用 pure dense 检索已经够了，如果做垂直任务，会针对任务再查具体应该用哪些方法。

> **AI**：这是本场比较明显的失分点。面试官问的是"检索范式判断"，你回答成了"我的项目够用"。更好的答案应该承认没有银弹：文本检索/BM25 对精确词、专有名词、编号、公式更强；Dense 对语义泛化和同义表达更强；未来更可能是 hybrid retrieval + reranker + query rewriting，而不是单纯向量或单纯关键词。Agent 场景里，检索还会和工具调用融合：结构化数据走 API/MCP，非结构化知识走 RAG，代码/文件系统走 shell。这样回答会比"我项目够用"高级很多。

### Q7. 你是怎么管理多轮上下文的？

我会用结构化 state 管理整个对话，这是 session 层面的。比如用户选定了目标论文，我会把目标论文绑定到当前对话里，后续追问时先判断是否要更新绑定论文。因为多数情况下，用户是在围绕同一篇论文连续追问。

另外还有一层类似 skill 的全局记忆，把一些全局信息写在 Markdown 文档里，比如自我认知、论文库信息等。

> **AI**：回答不错，能说明你不是简单把历史消息塞进 prompt，而是做了结构化状态。可以再把层次说清楚：短期上下文是 chat history，任务状态是 session state，长期知识是 memory/skill 文档。面试官如果继续追问，可以说"每轮会做 target carry-over 和 target update，防止追问时重新 search 跑偏"。

### Q8. 有没有考虑不同用户的长期记忆或用户画像？

我说设计了一个长期 learning 文件夹，可以放很多 Markdown 文件。Skill 本身有 frontmatter，可以区分什么时候调用，但我暂时没有实现多用户画像。目前项目不区分用户，只区分 session。

> **AI**：诚实，但显得产品化程度不够。正确方向是：现在是 local single-user，所以 session 级别足够；如果多用户化，需要 `user_id/session_id` 作为命名空间，长期记忆按用户隔离，敏感信息要有权限控制和删除机制。用户画像不一定一开始就做复杂，可以先存偏好的论文领域、常用检索语言、常看作者/会议等低风险信息。

### Q9. 模型微调用什么方式？基座模型、数据量、设备、指标是什么？

用 LoRA/QLoRA 微调，因为卡不够。当时是公安项目，需要识别血液形态。血液形态不是通用知识，而是内部专门的分类标准，在线模型也不能用，所以需要微调。

基座模型是 Qwen2.5-VL 7B，用 LLaMA Factory 做微调。数据集大概 100 多张图片，主要是我对照图片人工标注形态。训练用两张 V100。最后在测试图片上血液形态判断准确率大概 75%。

> **AI**：这次比一面强很多，因为你把模型大小说准了：Qwen2.5-VL 7B，而不是一面里口误的 32B/8A100。数据、设备、工具、指标都有了。唯一不足是 baseline 没有数字。你说"基座完全乱答"可以理解，但面试官追问"有没有具体数字"时，最好说："基座没有按指定标签体系输出，所以严格标签匹配准确率接近 0；微调后按 golden CSV 做 exact match，达到 75%。"这样就把"乱答"转换成了可评估指标。

### Q10. 微调带来最大的提升是什么？会不会影响其他能力？

最大的提升是模型理解我在问什么了。基座模型不知道这些内部形态分类，会乱答，不会归到固定形态里。微调后能按我们的标签体系输出。当然可能会对常识能力造成影响，但这个模型只用于血液形态识别，所以影响暂时可以接受。

> **AI**：回答方向对。可以更底层一点："提升主要来自两点：一是让模型学会领域标签空间，二是让输出格式对齐业务要求。副作用是灾难性遗忘或泛化下降，所以这种模型最好只作为垂直分类器使用，不拿来做通用问答。"这样会显得你理解微调的收益和代价。

### Q13. 论文助手如果三四轮之后回答跑偏，你会按什么顺序排查？

我说这个问题其实遇到过。首先查中间工具调用结果是不是跑偏，比如后续明明还在问前一篇论文，但系统又重新 search 到别的论文。然后查大模型填充 state 时有没有幻觉，比如检索结果和 state 里写入的目标论文不一致，或者 evidence 不一致。如果工具调用和 state 都没问题，再看链路上的其他问题。

> **AI**：回答很好，是工程排障思路而不是空谈。顺序可以整理成四层：① 工具调用日志：有没有调用错工具/错论文；② state diff：target、intent、constraints 有没有被错误更新；③ retrieval evidence：召回内容是否支持答案；④ final synthesis：最后生成是否脱离证据。这个顺序非常适合 Agent 系统排查。

### Q14. Agent 方向上有没有喜欢的公司、团体或论文观点？

我说最近 coding agent 很火，很多模型出厂前都会做工具调用相关的强化学习或微调。我看了 Claude Code 的源码，虽然看不到闭源模型训练过程，但可以看工具编排。

Claude Code 给我的收获主要有三点：第一，它的 prompt 不是单层的，而是有静态 prompt 和动态注入 prompt；第二，它有子 Agent 机制，为了避免上下文过长，会开一个子 Agent 空间执行任务，最后只返回摘要；第三，它的安全权限控制很细，让我意识到 Agent 从实验室玩具变成真正可用的编程助手，中间有很多工程细节。

> **AI**：比 Q6 好很多。你终于讲出了具体观察：prompt 分层、子 Agent 压缩上下文、安全权限控制。这些都是行业产品级 Agent 和 demo Agent 的差距。小问题是你把 Claude Code 叫成了"训练标杆"，容易被追问模型训练论文。更准确说："Claude Code 是产品级 coding agent 的工程标杆，我主要学习它的 harness、权限和工具编排。"

如果一口气让 Codex 或 Claude Code 做完整任务，它有时会为了通过任务指标而硬编码。所以我会在每一步写验证，确保它不是靠硬编码过关。

### Q17. 如何判定每次 AI 执行完成？

首先会写 pytest 的断言测试，保证基础任务不能跑偏。论文助手这边，我本地有 115 篇论文，构造了 170 多个基础检索评测题。每次迭代优化都要保证这些题目上不能出现明显下降或直接崩掉。

> **AI**：这是加分回答。你不是只靠肉眼看效果，而是有 regression benchmark。建议把数字再校准一下：一面里你后来确认实际是 159 道题，不是 170+。面试口述可以粗略，但博客里最好保持和实际数据一致，避免后续简历/项目文档数字打架。

### Q18. 如果直接把论文交给 Claude Code，能否超过你的论文助手？

我先说成本会很高。面试官说先不考虑成本后，我解释：Claude Code 更通用，如果让它直接查 PDF，它要现场找 PDF 解析库、提取文本、必要时再做多模态分析。我的系统已经做过离线入库，查询时不需要重新处理，所以速度上肯定更快。

> **AI**：回答有一个核心点是对的：专用系统通过离线预处理换在线速度，通用 Agent 现场处理成本高。但还可以再补两个优势：① 专用系统有固定评测集和可回归指标，Claude Code 现场查没有稳定性保障；② 专用系统有证据链和反查页面，可以定位答案来源，通用 Agent 更像一次性脚本执行。

### Q19. 离线入库后，怎么保障入库数据和原始 PDF 含义一致？

我当时承认可能会有信息损耗。因为 RAG 需要切块、向量化，兼顾速度时不可能百分百保留原文语义。我在前端做了反查页面，如果能查到对应内容，答案就有证据；如果查不到，原文中也可能存在，只能保证到这种程度。

> **AI**：这道题面试官问得很好，你回答得有点保守。更好的答案应该分层保障：① 入库时保存 chunk 的 `paper_id/page/bbox/source_text`，答案能回溯到原文；② 图表块保存 caption、页码和渲染图像路径，必要时回到原图让 VLM 复核；③ 检索只是候选召回，不把向量结果当真相，最终答案必须引用 evidence；④ 对关键问题用评测集验证 hit@k 和 answer accuracy。承认信息损耗是对的，但要给出工程补偿机制。

## 反问

### Q1. 教育 BG 的 AI Agent 业务主要做什么？

面试官说这个岗位叫 AI 研发工程师，但内部包含很多不同岗位。有专门做 Agent 开发的，也有很多教育方向的 Agent，比如面向学校管理、教师、学生的 Agent。学习机本质上也可以看作学生学习 Agent。

> **AI**：这段信息很关键。它解释了为什么面试官会不断追问"业务里怎么落地"和"不只是设计底座"。讯飞教育 BG 更像是教育场景里的 Agent 应用系统工程，不只是 coding agent 或 agent framework。后续如果 HR 面或入职前沟通，可以多强调你愿意做业务落地，而不是只想研究底层框架。

### Q3. 还有哪些方面需要继续学习？
