## 问题

### Q1. 自我介绍

面试官好，我是OwEn，是武汉大学电子信息专业的学生，目前在跟导师做Agent方向。去年我第一次接触Agent，拿了一个Agent编排奖项，然后之后做了三个月的偏好学习相关研究，现在又在看工程方面的内容，年初自己做了一个rag个人项目，目前在带着本科生一起打KDD Cup，所以我接触过很多Agent框架和思想，并且也一直在跟进AI的发展，所以想应聘贵公司的AI研发，了解一下企业是怎么真正应用编排研究Agent的，嗯。

### Q3. 你的项目具体是想解决什么问题？为什么要做这么一个框架？

我的项目是基本本地Zotero论文的一个知识库检索问答系统。我做这个的初衷是因为，我本地其实有很多论文，大概一百多篇，但是当我突然想找某个概念的时候，Zotero自带的检索其实很不好用，而且我也很难做跨论文比较，所以出于这个目的我想开发这个系统。

> **AI**：回答清晰，动机真实。可以保持。

### Q4. 市面上有很多成熟的RAG、Agent系统，你的系统跟他们相比，有哪些优势、特点呢？

（告诉面试官自己主要是出于学习目的，从头开始构建问题、分析思路，尝试解决纵向问题。）

> **AI**：全场失分最大的问题之一。"出于学习目的"把项目定位成了玩具。面试官问的是差异化优势，应该给出具体的、可量化的差异点：① 自研 AgentRuntime 工具循环，100 行代码替代 LangChain 黑盒；② 13+ 确定性 Solver + 3 层证据校验（规则而非 LLM），从架构上防幻觉；③ 12 配置 × 159 题消融实验，数据驱动选择 Pure Dense + QE；④ 复合查询自动分解、LLM-judge 消歧——这些通用 RAG 系统没有。

### Q5. （接）你的架构中是怎么进行工具调用的？

我也参考了一些开源的内容，比如Claude code，我借鉴了它的工具调用形式，将工具定义好schema交给LLM选择，先做意图识别生成一个target，同时进行Plan，这里的Plan就是将工具名放入一个队列中，然后模仿claude code做了一些安全保护，比如单轮对话工具调用不超过6轮，总数不超20。

> **AI**：回答基本正确。可以补充亮点——队列优先 + LLM 重规划的模式、Router+Planner 合并省一次 LLM 调用、三层工具注册表（AgentToolSpec → RegisteredAgentTool → AgentToolExecutor）。

### Q6. 你提到你弃用LangChain改用自己的框架，你为什么会做出这个选择？

是这样的，一开始我想要快速实现一个Agent框架，但是后来发现在解决我的特定问题下，我需要的其实不是多Agent合作，而是需要Plan + 单Agent模式。所以其实自己写一个Agent就行了，虽然LangChain/LangGraph也可以实现这些功能，但是就要写复杂的条件Command，也就是说LangChain/LangGraph更适合工作流或者更适合需要适配多种不同模型商……

（面试官：也就是说，主要是出于降低代码复杂性方便维护，类似这种）（对）

> **AI**：回答正确，面试官主动帮你总结说明他认可你的判断。建议补充一句：LangGraph 的 StateGraph 是 DAG 语义，适合预定义分支流程；而我的场景是"Plan-then-Loop"混合模型——先用 Planner 生成初始计划队列，队列空了再动态重规划，用 LangGraph 表达反而绕。场景决定架构选择。

### Q7. 那在你自己开发的过程中，你觉得最有趣或者说最难的部分是哪里？

嗯，那我就说一个有趣的地方。之前我以为 BM25+Jieba 应该会有不错的效果，因为他们说这个可以降低高频词（比如Transformer）的干扰，但是我实际测试下来效果并没有那么好，还是经常召回到BERT、ViT之类的，反而是Pure Dense查询效果更好，但是解决这个Transformer问题，我最终用的事Query Enhancement技术，比如你看，LLM会在Query Enhancement中直接把Attention is All You Need脑补出来填在目标中。

> **AI**：全场最佳。有现象、有根因、有解决方案、有最终效果——这就是面试官想听到的"真实遇到问题→分析→解决"的完整闭环。

### Q8. 那如果说不依赖于大模型的知识，你觉得应该怎么做才能保证查询精度呢？

嗯，这个问题我考虑过，也做了一些实验。我分别用GPT-4o和目前新发布的Deepseek-v4-pro对自己构造的一百多个验证集进行验证，发现两者召回准确度是一样的（97%），对的还是对的错的还是多的。这取决于我的策略，我首先入库的时候会将论文的摘要做一个终结，也一并入库；然后，入库纯文本的时候，我还会通过正则尝试匹配一些专有名词，比如连续的英文缩写、wo propose、我们提出xxx这样的句式，当做元信息中的alias。所以，我们在碰到完全不了解的名词（比如AlignX）也能有效定义出Target。

> **AI**：核心结论正确（模型无关的检索精度取决于离线预处理质量），但回答偏散。可以更结构化："我做了三层离线增强。第一层摘要生成——入库时为每篇论文用 LLM 生成 120-200 字中文摘要；第二层 body_acronyms 提取——从正文正则匹配全大写缩写存为别名；第三层多语言引言模式匹配——覆盖中英文 30+ 种'本文提出/we propose'句式。三层完全离线，不影响查询延迟。"最终的结论更强：不同模型召回准确率一致，说明检索质量由数据和预处理决定，而非模型选择。

这个前端是Claude code做的，我只负责编排Agent，用这个前端是为了方便我调试。

> **AI**：回答简洁，没有问题。突出自己专注 Agent 编排而非前端细节，定位合理。

### Q10. 我看到你的请求在前端会有一个节点图，怎么生成出来的？

（我不知道有没有理解对面试官的意思）

我的节点图其实是相对固定的，从入口->意图合同->计划->工具循环->证据->Claim->校验->回答这个过程，所以节点不用动态绘制。只要在计划下面打印工具调用的顺序即可。

如果是做动态节点的生成，我们就需要在每次执行完一个步骤之后，返回一个字典，包含目前更新的状态，然后抽取这些状态在前端绘图。

> **AI**：前半段正确（流水线固定结构 + 高亮当前阶段），后半段跑偏去讲动态绘图方案了。实际上你的系统通过 18 种 SSE event type 驱动 UI 状态更新——contract 事件更新意图卡片，candidate_papers 事件更新检索结果列表，answer_delta 流式逐字渲染。按 event type 注册不同 handler 即可，不需要动态 DAG 渲染。这个可以更清楚地表达。

### Q11. 怎么做的多模态查询？

在入库的时候就会用unstructured的库里的hi_fes模式，识别出图片和表格块信息在哪，如果召回到了表格或者图片，会现场传给多模态模型gpt-4.1-mini。

> **AI**：回答太简略，应该展开入库到查询的完整闭环："入库阶段用 unstructured hi_res 做两阶段 PDF 解析——pypdf 全量扫描打分选出图表密集页（table_like_score / figure_like_score ≥ 2.5），然后 hi_res 定向精析提取 table/figure/caption 结构化块，按 bbox 空间距离自动匹配 caption。查询阶段 Router 识别到 figure 查询后调度 figure_solver——用 pdftoppm 把目标页渲染为 180 DPI 图片，连同 caption 和 query 发给 VLM 直接从图中提取结论。图像不入库向量化，走文本检索 + VLM 按需分析的路径。"

### Q12. 了解过MCP协议吗？有没有在项目中应用。

嗯了解过，在这个项目中我没使用过，但是在另一个新闻的项目中我在服务器上搭建了MCP服务，向公网中暴露，可以用这个MCP获取我的新闻json或者md。我对MCP的理解，大概相当于Agent的一个纵向的能力吧。

### Q13. （接）什么叫MCP是纵向的？

就是，相当于Agent的工具吧，对，就是类似于Agent可以使用的动态工具，比如我在询问一些事情的时候，比如Claude Code或者LangChain的官方，都是开放了MCP的链接，我可以向这个链接发送一个请求，然后传回MCP的id，这样我就能获取动态文档的内容。就是相当于是一个动态的工具调用。纵向主要还是相对于横向来说的，Agent之间的通信我叫做横向，这个也从一篇论文中看到的，A2A这种Agent通信协议叫横向，MCP是纵向能力。

> **AI**："纵向/横向"的比喻本身没问题，CS 里常用 vertical/horizontal。但表达可以更干净："MCP 是 Agent 的能力纵深——让 Agent 能调用外部工具和数据源（垂直方向的能力扩展）。A2A 是 Agent 之间的横向协作——多个 Agent 互相发现、委派任务。两者互补：MCP 解决单个 Agent 能做什么，A2A 解决多个 Agent 怎么协作。"

### Q15. 我看你简历上写了Docker，你具体怎么用过Docker呢，你觉得有什么优势

Docker的优势在于创建了一个小虚拟环境方便部署，比如我在Linux服务器上开发的内容，用Docker打包发布后，能直接在MacOS上使用。然后，Docker Compose可以一键启动很多服务，比如我的项目中，会启动Milvus、Agent服务等，可以避免手动启动的遗漏等。

> **AI**：回答方向对，但有两个事实偏差需要注意：① "小虚拟环境"——Docker 是容器化不是虚拟化。容器共享宿主机内核、没有独立 OS，比虚拟机轻量得多。面试官如果懂运维会纠正你，应该说"隔离环境"或"容器化环境"。② "Linux 打包能直接在 macOS 上使用"——严格来说是错的。Linux 容器依赖 Linux 内核，macOS 上 Docker Desktop 实际是跑了一个隐藏的 Linux 虚拟机来运行容器，不是直接跨平台。正确的表述是"通过 Docker 镜像保证环境一致性，开发/测试/生产使用同一个 image，消除'我电脑上能跑'的问题"。③ 可以补充分层构建——Dockerfile 里先 COPY requirements.txt 再 pip install，这样代码改了但依赖没变时直接复用缓存层，构建从几分钟降到几秒。总体来说结合了实际项目的 docker-compose 场景，比空谈概念好。

### Q16. 你提到你的检索入库是基于Milvus，它运行在哪？

### Q17. 现在比较流行的方案是Skill，你怎么理解Skill？

嗯，我是Skill这个概念是今年一二月流行起来的，现在也是Claude code这些coding agent的主推。我看了五月的一个实验，对MCP、Skill和纯CLI进行测试，结果竟然是 MCP < SKill < CLI，当然这不意味着MCP就没用了。实际上，我认为Skill做的工作类似于固定化提示词一类的工作，让Agent直接用bash来工作，他避免了MCP塞入大量工具定义造成的上下文爆炸，可以根据元信息动态载入文档，但是它只适合那些LLM可以用终端直接做到的事情，和技巧操作之类的，类似于说明书。所以我认为MCP和Skill应该算是一种互补的关系吧。

（这里我说的有点乱了。我草这里应该提一嘴MCP可以不依赖大语言模型的先验知识，做比如企业的文档肯定要使用）

我在两个方面用过Skill吧，首先是通过Skill做一个任务的长期分步，类似一个millstone一样的东西，让Agent一步一步执行，自己更新文档。这样确实可以有效避免上下文过长导致的问题，在长期项目中很有用。

另一点就是前面说的一些技能的介绍，在name写明skill名，然后description用英文写上什么时候用。这个我自己写的就比较少了，主要还是下载别人写好的Skill。当然我也拆看过些了些什么。

（打开https://skills.sh/，他表明没错他们公司的人目前也在广泛用这个下载skill，指出了他想要的skill-creator，说我没有实际使用过）

> **AI**：整个 Skill 部分回答偏乱，有几个偏差需要纠正：① Skill 不只是"固定化提示词"——核心是**按需加载上下文**。Skill 触发前只有 name + description（两行），LLM invoke 后才注入完整文档，解决 MCP 全量 tool schema 塞入 system prompt 的上下文膨胀问题。② MCP vs Skill 的对比维度：Skill 的主体是指令（告诉 Agent 怎么做），MCP 的主体是工具（给 Agent 一个可调用的函数接口）。③ 面试官点名 skill-creator 你没用过，这个可以诚实说没实际用但了解原理。④ Skill 做任务分步（类似 milestone）是你用 Skill 的一种方式，但这不是 Skill 的标准定义——更像是在用 Claude Code 的 /plan 或 TODO 机制。

### Q22. （接）假设以后你的系统做大做强，有很多人在同步更改提交这个项目，或者做成了分布式，别人开发的过程中可能还要用旧缓存，那就不能清空了，你怎么做？

另一种方法，我觉得可以复杂化Key的结构，加入prompt或者上下文，这样迭代后key就不一样，会新生成缓存。

嗯，这就是我能想到的两种方法。

> **AI**：Q20 回答正确。Q21 的"迭代时清空缓存"在单机场景可以接受。Q22 分布式场景的回答暴露了工程经验不足——"等大版本一起更新"没有公司会这么做。正确思路是**缓存键版本化**："在 key 里嵌入配置版本号或配置内容的哈希，如 `rag:cache:v2:<config_hash>:<query>`。改完提示词后更新版本号，新 key 天然不和旧缓存冲突。旧缓存等 TTL 自然过期。更工程化的做法是在部署流程里每次上线自动 flush 对应 prefix，或采用 cache-aside 模式写入时主动失效。"

> **AI**：全场最大硬伤。这道题在问 Python Web 框架的核心机制，对做基础平台的部门很关键。需要理解三层：① **装饰器层**——`@app.post("/path")` 把 async 函数注册到路由表，装饰器本质是 `func = decorator(func)`，路由信息存在 `APIRoute` 对象里；② **ASGI 协议层**——请求到达 Uvicorn → 解析为 ASGI 三要素 `(scope, receive, send)` → Starlette 根据 scope 的 path 和 method 查路由表 → 找到匹配的 `APIRoute` → Pydantic 校验 + 依赖注入 → 调用 handler 函数 → 返回值序列化为 JSON → 通过 `send` 发回；③ **自己实现**——核心三步：路由注册（装饰器存映射表）、请求匹配（URL → handler）、响应序列化（dict → JSON + status code）。建议读 Starlette 源码的 routing.py 和 middleware.py。
