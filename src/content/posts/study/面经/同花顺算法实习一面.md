好的。我叫胡骏逸，是来自武汉大学电子信息专业的学生。我目前主要做的方向是和导师一起做 Agent 和强化学习方面的研究。

### Q3. 多模态 Agent 系统主要做了什么？贡献点是什么？

主要就是想把本地论文用一些概念检索出来。有些概念不在论文标题中，Zotero 这个论文软件的检索也不是很好用。我想做到突然想到一些名词概念，就可以快速检索到对应论文，然后提取出核心结论。

> **AI**：动机讲清楚了，但"贡献点是什么"没有直接回答。可以补三点：① 两层入库：paper card + evidence chunk；② query enhancement + structured state 提升检索准确率和速度；③ 多模态按需解析：图表元信息召回，命中后渲染原页给 VLM。

### Q4. 具体怎么做？

可以。首先我本地论文库是我自己看过的一些论文，大概 100 多篇，然后我把它先做了离线入库。我做的是两种层级的入库。

一种是 paper card 方面的入库。我先把每个论文的摘要、标题、作者这些元信息都放到一个 paper card 当中，这样每个论文都会有一个 paper card。

然后我再对论文证据级进行一个召回。我会用 Unstructured 库的 hi_res / fast 相关模式来提取每个页面的表格和图片。虽然我不会当场解析成多模态入库，但是会标记页码，然后把图片和表格的描述、上下文描述一并入库，作为一个 figure 或 table 的 block。如果召回到了这些 block，我就会现场发送给多模态模型去查询相关信息，然后再返回。

Agent 方面的检索，我是参考了 Claude Code 的 execute and planning 模式。首先会对 query 进行一次加强，让大语言模型重写 query，然后提取结构化查询数据。比如说查询目标是什么，需要解决的问题是表格类、图表类、最早提出的论文，还是关系类的论文，把这些东西都结构化保存，然后再进入下一个环节。

Plan and Execute 的过程是，我会把一些原子工具的使用放进队列中，直接从队列一个一个拿出去执行工具，然后得到结果。接着我会拿到一些论文块，然后抽取这些论文块的 claim。claim 中都包含 paper ID 和 evidence ID，然后再进行一致性检查，看会不会出现幻觉之类的情况。最后再让大语言模型 compose 一次，看现有证据能不能回答这个问题。如果能回答就直接给出答案，不能的话就让用户 verify，或者用 LLM as judge。大概就是这些流程。

> **AI**：这道题信息量足，基本把项目主线讲出来了：离线入库、图表元信息、query enhancement、工具队列、claim/evidence 校验、最终 compose。小问题是有点一口气讲太长。面试里可以先给总览："离线阶段做 paper/card/evidence 多层索引，在线阶段做 query rewrite、工具队列检索、证据校验和回答生成。"然后再展开。

图表的话也是刚刚说的，只存了图表的上下文元信息。需要用的时候把整页渲染成 PNG，然后发给多模态模型，让它返回所需要信息。

面试官继续确认：图片也是通过描述、标题这种来检索是吧？

### Q7. Agent 编排流程体现在哪里？

> **AI**：回答偏简略。面试官问"Agent 编排体现在哪里"，可以更具体：Planner 把任务拆成工具序列，队列执行 search/read/visual analysis 等原子工具，执行结果写入 state，必要时由 LLM 判断是否补检索或进入 compose。这些才是编排本体。

### Q8. RAG 检索有做什么优化吗？

RAG 检索我做的优化主要是两个层面。

一方面是检索策略上，我专门把几种常见的，比如多路召回、融合 RRF、BM25 检索这些东西拿出来。因为我自己拿论文做了一个很小的测试集：如果我要检索论文，最核心目的就是找到论文。然后我按难度划分，比如核心概念在标题中和不在标题中这些，都做成测试集，大概有 170 多题。然后我在此基础上用每一个策略试召回率，最后发现 Pure Dense 召回率最好。于是我否定了一开始设计的多路融合方案。

第二个主要是 Query Enhancement。一开始想直接用 query 查，事实上速度反而更慢。因为我调用一次大语言模型，把它提取成结构化结果。虽然调用了一次大语言模型，但是查询 query 更固定，target 也更短，反而速度从 1 秒降到了 800 毫秒左右。所以 Query Enhancement 速度也加快了，准确度也提高了。这两个是我做的主要优化。

> **AI**：这是全场比较好的回答。有评测集、有策略对比、有反直觉发现。两个亮点：① 数据驱动地否定 BM25/RRF 多路融合，不是拍脑袋；② LLM query enhancement 虽然多一次调用，但结构化后检索更快更准。注意数字还是建议统一，之前你复盘实际题数可能是 159，不一定是 170+。

### Q10. 讲一下 AIOS 多 Agent 新闻编排系统

这个 AIOS 是去年 7 月到 10 月开始做的项目，是一个开源项目改过来的。它的核心目的是提供一个 AIOS 框架，想给 AutoGen、LangChain 这些多智能体协作 APP 提供一个共性的底层，相当于操作系统之于电脑的地位。

它会把上层 Agent 发来的请求抽象成四个 query：Tool Query、LLM Query、Memory Query 和 Storage Query。抽象成四个 query 之后，会提供四个队列，让这四个 query 按照调度策略进行。它本身提供了两种调度策略，一种是先进先出，一种是时间片机制，会模拟操作系统去调用。

这个比赛本身是想让你设计多 Agent，数量有要求，多个 Agent 之间必须合作。我做的是一个新闻生产系统。首先用 Python 线程库将每个新闻部分并行。因为当时要求端侧大模型，只能用 7B，所以一次完成任务效果没有那么理想。于是我对每个部分用两个 Agent：一个生成，一个 critic，让它们互相交流，直到最后批准通过为止。

中间内容我没有用消息队列，因为最后也是要合成的，就直接用了一个中间文件存储格式，存 text。最后校验合并成新闻本体，然后渲染发布。就是这样一个过程。

> **AI**：回答很完整。你把 AIOS 的抽象层讲出来了：Tool/LLM/Memory/Storage 四类 query + 调度策略。对面试官来说，这比只说"我做了多 Agent 新闻"更有工程感。可以补一句"文件存储是比赛约束下的轻量方案，如果生产化会换成消息队列或状态机"，会更成熟。

### Q11. 新闻编排系统能不能举个例子？输入是什么，输出是什么？

这个新闻编排场景实际上是一种推送类项目。我启动在自己的云端服务器上，在推送新闻。

它不需要用户输入，因为有一个 API 接口，我使用热搜 API 从各个平台拿到热搜。第一步用搜索 Agent 对热搜去重、重新编写，防止各个平台有重复热点。然后再用每一个热点去搜索，搜索得到的结果再创造一个综合新闻报。

也就是说，每天早上 10 点钟启动，直接生成新闻报。通过 MCP 会推送一个 Markdown 文件，本地也会生成一个 HTML 文件，然后渲染到前端。是这样一个过程。

> **AI**：这个例子不错，说明项目已经从比赛 demo 变成了线上定时任务。关键词可以再强化：定时触发、热搜聚合、去重、搜索增强、生成-审阅、Markdown/HTML 输出、MCP 暴露。这些和同花顺"主动投资助手"的业务其实有相似性：都是从外部事件触发 Agent 工作流。

### Q13. 基于记忆的编辑门控是什么？记忆体现在哪里？

可以。因为 AIOS 本身有一个 Storage 功能，我也用到了本地存储。每次生成新闻，我都会把以前的新闻判断结果放进去。最后在生成新闻之前参考一下有没有出现以前这些新闻。如果有出现的话，就可以提高它通过的概率。

这个只是可行门控的一个方面。另外的可行门控还有：网页搜索过来的东西，它的标题和现在新闻是否匹配；证据是不是为空之类的。这些可行性系统都有一个加权分数。后来分数通过阈值，我才会把这个新闻输出。是这样一个过程。

> **AI**：思路对，但"出现以前这些新闻就提高通过概率"听起来可能怪，容易像重复新闻反而更容易通过。更准确可以说：历史记忆用于识别重复/持续热点和历史判断结果；门控综合标题匹配、证据充足性、重复度、来源可信度等打分，超过阈值才进入生成。这个和金融 Agent 里的用户画像/历史交易记忆很像，应该重点说"记忆参与决策"。

### Q15. 简单讲一下 DPO 和 GRPO 的区别

好的。DPO 和 GRPO 应该同属于从 PPO 方面进行的优化。它们两个有个共性，就是都想去掉 PPO 的复杂奖励函数。

DPO 做的事情就是，它把 BT 模型反解，然后代入到原本的奖励函数中。我就发现可以直接对策略模型进行优化，不需要再训练奖励函数了。这就是 DPO 做的直接优化。它需要的数据只是一个 chosen 和 rejected 的对，然后进行一个交叉熵损失，就是 log，这样直接优化就可以了。这也是比较方便、可以离线做的一种训练。

GRPO 的话，它就是想通过相对优势的方式来选出优势函数。每次让模型生成几个回答，然后用平均回答的奖励来定义每个回答相对于这一组的优势是多少。这样我就不用计算绝对奖励了，也是进行了一个优化。这是我的理解。

> **AI**：比字节那场答得好一些，至少把 DPO 的 chosen/rejected 和 GRPO 的组内相对优势讲出来了。但仍有两点不准：① GRPO 不是去掉奖励函数，而是去掉 critic/value model，仍然需要 reward/verifier；② DPO loss 不是普通交叉熵，核心是比较 policy 相对 reference 在 chosen/rejected 上的 log-prob 差值，并由 `beta` 控制偏离 reference 的强度。面试官后面追 beta，说明他在听这个细节。

### Q16. DPO 损失函数里的 beta 是干嘛的？

beta 相当于 DPO 的，可以说是温度一样的东西吧。它加在后面的损失前面。一般我会调它，比如觉得训练 loss 下降不太快，就会调大它。

面试官追问：你知道 DEPO 吗？

我回答：其他可能不太了解。

> **AI**：这题分成两层。第一层是 `beta`：DPO 里的 `beta` 可以理解为控制 policy 偏离 reference model 的强度，也影响偏好差异的 sharpness。`beta` 越大，模型越强地放大 chosen/rejected 的偏好差异，但也可能更激进；`beta` 越小，更新更保守，更贴近 reference。不要说成"loss 降不快就调大"，这像是凭感觉调参。第二层是面试官追问的 **DEPO**：它不是 DPO 口误，而是 **Dual-Efficiency Preference Optimization for LLM Agents**，面向 Agent 场景，同时奖励回答简洁和更少 action steps，用偏好优化让 Agent 在保持任务效果的同时减少 token 和步骤开销。你这里不知道可以接受，但说明同花顺确实在关注 Agent 效率优化。

### Q18. 怎么保证 AI coding 出来的代码是你需要的代码？

现在的话，过去还需要手工看一下，然后每一步一个模块一个模块做。

现在比较常用的方法就是，先把要求还有需要测试的东西都写好。比如说我把需要做的东西按照 milestones 的方式，一步一步写到一个 skill 文件，或者写到固定化文档里面。Codeium 的 Code 本身也有 planning 模式。或者用 Claude Code 的话，把这个文档显式放在项目文件夹下，让它每次更新的时候同步更新文档，也就是每次会动态载入总要求。这是第一个。

第二个就是用 git 工具，保证每次都是可回滚的。因为确实有时候很会改坏。每次让它自动提交，用 GitHub 插件提交到自己个人仓库，然后随时能回退。就保证这两个点：一是不改坏，二是可以稳定推进项目。

> **AI**：回答不错，和你前几场一致：milestone + 验收标准 + git 可回滚。还可以再补第三点：自动化测试/最小 demo 验证。只靠文档和 git 只能保证方向和回退，真正保证"是我要的代码"还需要 pytest、端到端脚本、评测集或截图检查。

### Q19. Claude Code 的记忆机制、上下文压缩管理了解吗？

Claude Code 有了解过。我之前泄露出来的时候稍微看过一点源码。

Claude Code 的 memory 机制主要还是通过本地文件夹存储，比如对话记录、MCP 调用回来的 prompts 和上下文之类的，都会在本地 `.claude` 文件夹下创建一个 session 文件夹，大部分放在里面。

另外一个当时没想到的 memory 机制是子 Agent 做了上下文隔离。其实这也是现在通用的一种方式：主 Agent 在调用任务的时候隔离上下文，防止上下文撑爆。让子 Agent 只返回最后一个执行任务结果的摘要，这样就可以分步很多任务下去。

另外它还有一个比较神奇的机制，就是有一个做梦的机制，会自动整理自己的记忆，变成更精简、更简短的类型，方便以后继续使用。关于用户偏好之类的永久记忆就比较容易理解，就是记录一个总文档。

> **AI**：这题回答有亮点：本地 session、子 Agent 上下文隔离、摘要压缩、长期偏好文档都讲到了。注意不要把你不确定的源码细节说得太绝对，比如"做梦机制"可以改成"类似 memory compaction / summarization 的机制"，会更稳。面试官问这个其实是在看你对 Agent 长上下文管理有没有产品级理解。

### Q24. Coding：生成有效括号

面试官从题库随机选了一道题，让我写。题目是生成有效括号。

我一开始写错了，执行卡住，应该是递归条件导致无限循环。后来我讲思路：

这个生成有效括号组合，就是给一个输入 `n`，需要不断看 left 和 right 的关系。我忘了一个事：left 和 right 都不能超过 n，有效括号还必须保证 right 不能超过 left。

做法就是 DFS 一位一位往下看。如果现在 left 不超过 n，可以继续加左括号，然后递归进去，left 加一。递归右括号的话，必须满足 right 小于 left，才能加右括号，然后 right 加一。到了如果合法，`path.length == n * 2` 的时候，就把 path 加到 ans 当中。

> **AI**：这题是 Hot100 级别，错了确实很亏。核心条件是：`left < n` 可以加 `(`；`right < left` 可以加 `)`；当 `path.length == 2 * n` 收集答案。你现场的主要问题是漏了 `right < left`，导致非法分支甚至递归异常。建议最近把回溯模板重新过一遍：括号生成、组合总和、子集、全排列、电话号码字母组合。
