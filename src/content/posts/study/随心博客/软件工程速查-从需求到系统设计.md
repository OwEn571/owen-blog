# 一、为什么突然补软件工程

字节二面邮件里写了一句：

> 提前温习软件工程的核心概念，例如：如何从一个需求落实到一个系统设计，如何衡量两个不同设计的好坏，如何在各种限制下（人员、时间、资源等）选择其中更合适的设计，以及提升该设计的可拓展性等。

这句话一开始看起来像要补一整门本科软件工程课，但其实不是。

面试里的“软件工程核心概念”更像是一种思维方式：

> 给你一个模糊需求，你能不能澄清目标、拆成模块、设计数据流、比较方案，并在有限时间和资源下选择一个可落地的实现。

它不重点考 UML、瀑布模型、敏捷宣言这些课本内容。它更关心：

- 你是否知道先问需求，而不是直接写代码。
- 你是否能区分核心功能和边缘功能。
- 你是否能说清楚一个系统有哪些模块。
- 你是否能比较两个方案的好坏。
- 你是否知道什么情况下先做 MVP，什么情况下上复杂架构。
- 你是否考虑可扩展、可回滚、可观测和安全。

所以这篇不是软件工程教材，而是面试速查。

# 二、一句话模板

如果面试官给一个系统设计题，可以先按这句话走：

> 我会先澄清需求和约束，再拆核心功能和非功能指标，然后设计模块和数据流。方案上先给一个最小可行版本，再说明如果数据量、并发、人力或稳定性要求提升，系统可以怎么演进。

这句话背下来就已经能稳住开头。

完整流程是：

```text
需求澄清
-> 核心功能
-> 非功能指标
-> 模块拆分
-> 数据流
-> 方案比较
-> 取舍理由
-> 扩展性设计
-> 监控、安全、回滚
```

# 三、第一步：需求澄清

系统设计最忌讳的是一上来就说“我准备用 Redis / Kafka / Neo4j”。

先问需求。

常见澄清问题：

```text
谁用这个系统？
核心目标是什么？
输入是什么？
输出是什么？
数据规模多大？
实时性要求多高？
准确性要求多高？
是否涉及隐私和权限？
是先做 demo，还是要生产可用？
人力、时间、机器资源有什么限制？
```

比如面试官说：

> 设计一个训练数据处理系统。

可以先问：

- 数据来源是用户日志、人工标注、合成数据，还是外部数据？
- 数据规模是每天几万条，还是几亿条？
- 处理是离线批处理，还是实时流式？
- 数据是否包含用户隐私？
- 最终服务 SFT、DPO、RLVR，还是评估集构建？
- 是否需要人工审核和版本管理？

这些问题不是拖时间，而是在定义系统边界。

# 四、第二步：拆核心功能

需求澄清后，要把系统拆成几块。

一个通用拆法：

```text
输入层：数据从哪里来
处理层：怎么清洗、转换、标注、评估
存储层：数据和元信息存在哪里
服务层：下游怎么消费
管理层：权限、版本、监控、回滚
```

以训练数据 pipeline 为例：

```text
数据接入
-> 清洗去重
-> 脱敏
-> 标注 / 合成
-> 质量评估
-> 数据版本管理
-> 训练 / 评测消费
-> 线上反馈回流
```

这已经是一个可讲的系统设计。

# 五、第三步：定义非功能指标

功能是“系统能做什么”，非功能指标是“系统要做得多好”。

面试里常见非功能指标：

| 指标 | 要问的问题 |
| --- | --- |
| 正确性 | 结果是否符合业务目标？ |
| 延迟 | 用户或下游系统能等多久？ |
| 吞吐 | 每天/每小时要处理多少数据？ |
| 成本 | 算力、存储、人力是否可接受？ |
| 可扩展性 | 数据量变大、功能变多时能否扩展？ |
| 可维护性 | 代码和模块是否容易理解、修改？ |
| 可观测性 | 出错后能否定位原因？ |
| 安全性 | 是否有隐私、权限、泄露风险？ |
| 可回滚 | 新版本出问题能否恢复？ |

面试时可以说：

> 除了功能本身，我会重点关注数据质量、处理吞吐、可追溯性、权限安全和版本回滚。因为训练数据一旦污染，会直接影响模型效果，而且问题很难事后定位。

这很适合飞书 AI 数据与安全岗位。

# 六、第四步：设计模块和数据流

系统设计要画图时，可以先画数据流，不急着画部署图。

一个训练数据系统可以这样说：

```text
数据源
  -> Ingestion Connector
  -> Raw Data Store
  -> Cleaning Worker
  -> Dedup / PII Filter
  -> Labeling / Synthetic Data Generator
  -> Quality Evaluator
  -> Versioned Dataset Store
  -> Training / Evaluation Jobs
  -> Online Feedback
  -> Badcase Mining
  -> 下一轮数据迭代
```

每个模块职责要单一：

- `Connector` 负责接入数据源。
- `Cleaner` 负责清洗格式、过滤脏数据。
- `Dedup` 负责近重复检测。
- `PII Filter` 负责隐私脱敏。
- `Labeler / Generator` 负责人工标注或模型合成。
- `Evaluator` 负责质量打分。
- `Dataset Store` 负责数据版本管理。
- `Consumer` 负责给训练、评估、分析任务使用。

如果能这样拆，面试官一般会觉得你有工程意识。

# 七、第五步：比较方案

邮件里说“如何衡量两个不同设计的好坏”，就是让你会比较方案。

不要只说“方案 A 更好”。要说：

> 在当前约束下，方案 A 更合适；如果约束变化，方案 B 可能更合适。

## 例子 1：JSON / SQLite / Neo4j

假设要做轻量 Graph RAG。

| 方案 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- |
| JSON | 最简单，易展示，无服务依赖 | 查询能力弱，不适合大规模 | 面试 demo、小数据 |
| SQLite | 单文件、支持 SQL、比 JSON 稳 | 图遍历不如图数据库自然 | 中小规模、本地原型 |
| Neo4j | 图查询强、关系表达自然 | 部署和运维重，学习成本高 | 大规模图谱、多人共享 |

面试回答：

> 这次只有 100 多篇论文，而且是课后作业验证 graph index 的检索价值，所以我先用 JSON/SQLite 做轻量实现。如果未来扩到百万级文档，或者需要多人维护图谱、复杂 Cypher 查询和权限管理，再迁移到 Neo4j。

这就是方案取舍。

## 例子 2：离线批处理 vs 实时流式

| 方案 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- |
| 离线批处理 | 简单、稳定、成本低、容易回滚 | 延迟高 | 日级训练数据处理 |
| 实时流式 | 延迟低，反馈快 | 架构复杂，调试难 | 实时推荐、实时风控 |

面试回答：

> 如果训练数据每天更新一次，离线批处理更合适；如果是线上安全拦截或实时推荐，才需要流式架构。不要为低频需求过早引入复杂实时系统。

## 例子 3：规则过滤 vs 模型判别

| 方案 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- |
| 规则 | 快、便宜、可解释 | 覆盖有限，维护规则麻烦 | PII、格式、黑名单 |
| 模型 | 泛化强，能处理语义 | 成本高，可能误判 | 质量评分、语义安全、复杂分类 |

面试回答：

> 我会先用规则处理确定性强的问题，比如手机号、邮箱、空字段、格式错误；再用模型处理语义质量和复杂安全判断。这样成本和效果比较平衡。

# 八、第六步：在限制下做取舍

面试官很可能问：

> 如果只有两天时间，你怎么做？

或者：

> 如果只有一个人、没有太多机器资源，你怎么选？

可以用这个模板：

```text
如果人少、时间紧、数据量小：
先做 MVP，选择简单方案，验证闭环。

如果数据量变大、多人协作、稳定性要求高：
再拆模块，引入队列、任务调度、数据库、版本管理、监控和权限控制。
```

具体到项目：

```text
100 篇论文：
JSON / SQLite + 本地脚本 + 简单 RRF。

10 万篇论文：
向量库 + 图数据库 + 异步构图任务 + 数据版本管理。

生产系统：
权限控制 + 监控告警 + 数据质量看板 + 回滚机制 + 成本统计。
```

这比一上来堆技术名词更有说服力。

# 九、第七步：可扩展性怎么讲

可扩展性不是“我用微服务所以可扩展”。

更好的回答是：

> 我会让变化频繁的部分和稳定部分解耦。

常见手段：

## 1. 模块化

把系统拆成独立模块：

```text
数据接入
清洗
脱敏
标注
评估
存储
训练消费
```

新增功能时只改对应模块。

## 2. 稳定 schema

模块之间通过稳定数据格式传递。

例如：

```json
{
  "sample_id": "xxx",
  "source": "user_feedback",
  "text": "...",
  "labels": {},
  "quality_score": 0.91,
  "version": "2026-06-01"
}
```

数据 schema 稳，模块才能独立演进。

## 3. 配置化

容易变的东西不要写死：

- 清洗规则
- 过滤阈值
- prompt
- 模型名称
- 数据源路径
- 评估指标

这些应该放配置里。

## 4. 异步解耦

耗时任务用队列或任务系统解耦：

```text
上传数据 -> 写入任务队列 -> worker 清洗/标注/评估 -> 写入结果
```

这样某个 worker 挂了，不会拖垮整个系统。

## 5. 版本管理

训练数据必须能追溯：

- 原始数据版本
- 清洗规则版本
- prompt 版本
- 标注版本
- 评估指标版本
- 最终 dataset 版本

否则模型变差时很难定位问题。

# 十、飞书岗位高频系统设计题

结合这几次面试，飞书这个岗位更像训练数据系统 / 数据合成 / 数据安全方向。

重点准备下面四类。

## 1. 设计一个训练数据处理 pipeline

可以这样讲：

```text
数据源：用户反馈、产品日志、人工标注、模型生成数据
接入：connector 定时拉取或上传
清洗：格式统一、乱码过滤、语言检测
去重：hash / simhash / embedding 近重复
脱敏：手机号、邮箱、姓名、公司敏感信息
标注：人工标注或 LLM 辅助标注
质检：规则 + 模型 + 抽样人工审核
版本：dataset version + metadata
消费：SFT / DPO / eval / badcase analysis
反馈：线上 badcase 回流
```

非功能指标：

- 数据质量
- 可追溯
- 权限安全
- 处理吞吐
- 成本
- 可回滚

## 2. 设计一个数据合成系统

流程：

```text
定义任务类型
-> 设计 seed prompts
-> LLM 生成样本
-> 规则过滤
-> 模型评分
-> 去重
-> 人工抽检
-> 加入候选训练集
-> 小规模训练验证效果
```

关键点：

- 合成数据不能直接进训练集，要质检。
- 要防止模式坍缩：生成样本太像。
- 要做多样性控制：领域、难度、风格、长度。
- 要保留 prompt 和模型版本，方便回溯。

## 3. 设计一个 LLM / Agent 评估平台

流程：

```text
评测集管理
-> 模型 / prompt / agent 版本选择
-> 批量运行
-> 自动打分
-> LLM judge / 人工复核
-> 结果对比
-> badcase 归因
-> 回流数据飞轮
```

指标：

- answer correctness
- faithfulness
- format accuracy
- tool call accuracy
- task success rate
- latency
- token cost
- unsafe rate
- regression rate

Agent 评估还要看：

- 工具调用次数
- 失败步骤
- 是否循环
- 是否违反权限
- 是否能从错误中恢复

## 4. 设计一个文档 RAG / Graph RAG 系统

流程：

```text
文档解析
-> chunk / metadata
-> dense index
-> paper card / summary index
-> concept graph index
-> query rewrite
-> dense retrieval
-> graph expansion
-> rerank / RRF
-> evidence selection
-> answer generation
-> citation / trace
```

方案取舍：

- 小规模：JSON/SQLite graph + Milvus。
- 大规模：向量库 + 图数据库 + 异步构图。
- 事实查询：dense retrieval 优先。
- 多跳关系：graph retrieval 加分。
- 高风险场景：必须引用 evidence。

# 十一、回答系统设计题的固定话术

可以直接背：

```text
我会先澄清需求：用户是谁、输入输出是什么、数据规模和实时性要求怎样、是否涉及隐私和权限。

然后先做 MVP，把核心链路跑通。比如这个系统可以先拆成数据接入、清洗脱敏、标注/合成、质量评估、版本存储和训练消费几个模块。

如果数据量不大，我会优先选择简单方案，比如离线批处理和单体服务，降低实现成本；如果后续数据量变大或者多人协作，再引入任务队列、worker、版本管理、监控告警和权限系统。

衡量方案时，我会看正确性、复杂度、成本、延迟、吞吐、可维护性、可扩展性和安全性。

最后，所有训练数据都要能追溯版本，因为数据污染或者规则变更会直接影响模型效果。
```

# 十二、和我已有项目怎么关联

我其实不是完全没有软件工程经验，只是以前没有把它抽象出来。

## 1. 论文 RAG 项目

可以对应：

- MVP：100 篇论文，先用 dense retrieval + query enhancement。

## 2. Graph RAG 作业

- 取舍：100 篇论文用 JSON/SQLite graph，不上重型图数据库。
- 扩展：未来可以迁移 Neo4j。
- 融合：dense 保底，graph 扩展，RRF 融合。

## 3. AIOS 新闻项目

可以对应：

- 需求：自动生成新闻日报。
- 模块：热搜抓取、去重、搜索、生成、审阅、合并、发布。
- 取舍：比赛场景用中间文件，生产场景可换消息队列。
- 评估：证据是否为空、标题是否匹配、历史记忆门控。

## 4. AI coding 使用经验

可以对应：

- 需求拆解：milestone 文档。
- 验收：pytest / demo / benchmark。
- 回滚：git。
- 可维护：模块边界和文档同步。

# 十三、一个具体案例：飞书文档助手 badcase 回流到模型训练

上面的框架还是有点虚。下面写一个具体系统，假设我是飞书 AI 数据团队，要做一个“文档问答助手”的线上 badcase 回流系统。

这个案例覆盖四个模块：

1. 训练数据处理 pipeline
2. 数据合成和质检系统
3. LLM / Agent 评估平台
4. 文档 RAG / Graph RAG 系统

## 1. 业务背景

飞书里有很多企业文档：

- 项目 PRD
- 周报
- 会议纪要
- OKR
- 需求文档
- 接口文档
- 知识库说明
- 审批制度

我们有一个文档助手，用户可以问：

```text
“帮我总结一下 A 项目的延期原因。”
“上周产品例会里谁负责灰度发布？”
“这个需求的验收标准是什么？”
“A 项目和 B 项目的依赖关系是什么？”
```

线上问题是：模型经常答得像真的，但其实引用错文档、漏上下文、或者把多个项目混在一起。

一个真实 badcase 可能是：

```text
用户问题：
“A 项目这周延期的主要原因是什么？有没有影响 6 月上线？”

模型回答：
“主要原因是前端资源不足，预计不会影响 6 月上线。”

真实情况：
文档里写的是“后端接口联调阻塞，灰度时间从 6 月 5 日推迟到 6 月 12 日，可能影响 6 月正式上线”。

错误类型：
1. 检索召回了上个月的会议纪要，而不是本周纪要。
2. 模型没有识别“这周”的时间约束。
3. 回答没有引用 evidence。
4. 把另一个项目的“前端资源不足”串进来了。
```

目标不是简单修这一个回答，而是把这个 badcase 变成模型能力提升的材料。

## 2. 总体系统设计

整体链路：

```text
线上用户请求
-> RAG / Agent 生成回答
-> 用户反馈 / 自动检测 badcase
-> badcase 入库
-> 脱敏清洗
-> 错误归因
-> 数据标注 / 合成
-> 评估集更新
-> SFT / DPO / RLVR 数据构造
-> 小规模训练或 prompt / retriever 调整
-> 离线评估
-> 灰度上线
-> 继续收集反馈
```

这就是数据飞轮：

```text
线上失败 -> 数据加工 -> 训练 / 评估 -> 上线验证 -> 再收集失败
```

## 3. 模块一：线上 badcase 采集

每次文档助手回答，都记录一条 trace：

```json
{
  "trace_id": "trace_20260601_000123",
  "user_id_hash": "u_xxx",
  "tenant_id": "tenant_abc",
  "query": "A 项目这周延期的主要原因是什么？有没有影响 6 月上线？",
  "answer": "主要原因是前端资源不足，预计不会影响 6 月上线。",
  "retrieved_docs": [
    {
      "doc_id": "doc_old_meeting_0510",
      "chunk_id": "chunk_12",
      "score": 0.82,
      "text": "A 项目本月前端资源不足..."
    }
  ],
  "tool_calls": [
    {
      "tool": "doc_search",
      "arguments": {
        "query": "A 项目 延期 原因 上线"
      },
      "latency_ms": 130
    }
  ],
  "model": "internal-chat-v3",
  "prompt_version": "rag_prompt_2026_05_31",
  "retriever_version": "hybrid_retriever_v2",
  "created_at": "2026-06-01T10:12:30+08:00"
}
```

注意：必须记录版本。

如果只记录 query 和 answer，以后根本不知道错误来自哪里。

badcase 可以从四个渠道来：

1. 用户点踩
2. 用户追问纠错，比如“你答错了，不是前端，是后端接口”
3. 自动检测，比如回答没有引用 evidence
4. 人工抽检

技术选型：

| 阶段 | 选型 | 理由 |
| --- | --- | --- |
| MVP | PostgreSQL 存 trace 和 badcase 状态 | 简单、够用、可查询 |
| 中等规模 | Kafka + PostgreSQL + 对象存储 | 请求日志和离线处理解耦 |
| 分析场景 | ClickHouse | 适合大量 trace 聚合分析 |
| 文档原文 | 对象存储 / 文档库 | 大文本不适合全塞关系库 |

面试里可以说：

> MVP 阶段我不会先上 Kafka 和 ClickHouse，可以先用 PostgreSQL 存 trace 和 badcase 状态。等请求量变大、分析需求变多，再把日志流接到 Kafka 和 ClickHouse。

## 4. 模块二：脱敏、清洗和错误归因

飞书文档可能包含：

- 用户姓名
- 手机号
- 邮箱
- 公司内部项目代号
- 客户名称
- 商业数据
- 合同金额

这些数据不能直接进入训练集。

规则脱敏：

```text
手机号 -> <PHONE>
邮箱 -> <EMAIL>
身份证 -> <ID_CARD>
金额 -> <AMOUNT>
URL -> <URL>
真实姓名 -> <PERSON>
公司名 -> <ORG>
```

模型辅助脱敏：

- 识别项目代号
- 识别客户名称
- 识别内部组织名
- 识别上下文里的隐私实体

技术选型：

- 第一层用正则和规则，便宜、稳定、可解释。
- 第二层用 NER / LLM 做语义脱敏，覆盖规则识别不了的内部名词。
- 脱敏前原始数据只保存在高权限存储，训练集只用脱敏后版本。

每个 badcase 要标错误类型：

```json
{
  "trace_id": "trace_20260601_000123",
  "error_type": [
    "retrieval_wrong_doc",
    "time_constraint_missed",
    "hallucinated_answer",
    "missing_citation"
  ],
  "severity": "high",
  "should_enter_eval": true,
  "should_enter_training": true
}
```

错误类型可以分成：

| 类型 | 例子 | 应该怎么修 |
| --- | --- | --- |
| retrieval_wrong_doc | 召回旧文档 | 改 retriever / 加时间过滤 |
| retrieval_missing_doc | 关键文档没召回 | 加 query rewrite / hybrid retrieval |
| reasoning_error | evidence 对但推理错 | SFT / DPO |
| format_error | 没按 JSON 输出 | SFT |
| hallucination | 没证据乱答 | evidence 约束 / DPO |
| tool_error | 工具参数错 | tool-use SFT |
| permission_error | 读了无权文档 | 权限系统 |
| missing_citation | 没引用来源 | prompt / SFT |

关键判断：

> 不是所有 badcase 都应该拿去训练。要先判断错误来源。如果是检索错，就优先修 retriever；如果是答案风格或格式错，再考虑 SFT；如果是偏好问题，再考虑 DPO。

## 5. 模块三：把 badcase 变成 SFT 数据

如果错误是：

- 格式不对
- 没引用 evidence
- 没按结构回答
- 对已有 evidence 总结不好

可以构造成 SFT 数据。

原始 badcase：

```text
query:
A 项目这周延期的主要原因是什么？有没有影响 6 月上线？

wrong_answer:
主要原因是前端资源不足，预计不会影响 6 月上线。

gold_evidence:
本周项目例会纪要：后端接口联调阻塞，灰度时间从 6 月 5 日推迟到 6 月 12 日，可能影响 6 月正式上线。
```

SFT 样本：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是企业文档问答助手。回答必须基于给定证据；如果证据不足，需要明确说明；回答必须引用来源。"
    },
    {
      "role": "user",
      "content": "问题：A 项目这周延期的主要原因是什么？有没有影响 6 月上线？\n\n证据：本周项目例会纪要：后端接口联调阻塞，灰度时间从 6 月 5 日推迟到 6 月 12 日，可能影响 6 月正式上线。"
    },
    {
      "role": "assistant",
      "content": "A 项目本周延期的主要原因是后端接口联调阻塞。根据本周项目例会纪要，灰度时间已从 6 月 5 日推迟到 6 月 12 日，因此可能影响 6 月正式上线。"
    }
  ],
  "metadata": {
    "source": "online_badcase",
    "error_type": ["reasoning_error", "missing_citation"],
    "trace_id": "trace_20260601_000123",
    "dataset_version": "sft_docqa_20260601"
  }
}
```

如果原问题是检索没召回正确文档，那么不能只做 SFT。

因为模型根本没看到正确证据，训练它怎么答也没意义。

应该先修：

- query rewrite
- 时间过滤
- hybrid retrieval
- rerank
- 权限过滤

## 6. 模块四：把 badcase 变成 DPO 数据

如果错误是：

- 两个答案都能回答，但一个更符合用户偏好
- 一个更简洁、一个更啰嗦
- 一个有引用、一个没引用
- 一个更安全合规

可以构造成 DPO 数据。

DPO 偏好对：

```json
{
  "prompt": "基于证据回答：A 项目这周延期的主要原因是什么？有没有影响 6 月上线？\n证据：后端接口联调阻塞，灰度时间从 6 月 5 日推迟到 6 月 12 日，可能影响 6 月正式上线。",
  "chosen": "A 项目延期的主要原因是后端接口联调阻塞。灰度时间从 6 月 5 日推迟到 6 月 12 日，因此可能影响 6 月正式上线。",
  "rejected": "A 项目延期主要是资源不足，但预计不会影响上线。",
  "metadata": {
    "preference_reason": [
      "chosen is grounded in evidence",
      "chosen mentions schedule impact",
      "rejected hallucinates resource issue"
    ],
    "source": "online_badcase"
  }
}
```

DPO 在这里不是学一个新事实，而是在学偏好：

- 有证据的回答优于没证据的回答。
- 明确指出风险优于含糊安慰。
- 引用当前文档优于混入旧文档。
- 不确定时说明不确定优于编答案。

面试回答：

> 对于文档助手，DPO 可以用来强化“有证据、少幻觉、符合格式、风险表达清楚”的回答偏好。它不替代检索系统，而是在检索结果正确的前提下，让模型更倾向于输出用户和业务更认可的答案。

## 7. 模块五：可验证任务怎么做 RLVR / GRPO

不是所有任务都适合 RLVR。

适合 RLVR 的任务通常有可自动验证的结果，比如：

- JSON 格式是否合法
- 引用的 doc_id 是否存在
- 回答是否只引用了允许文档
- 工具调用参数是否符合 schema
- SQL 是否能执行
- 代码是否通过测试

一个回答可以被规则打分：

```text
+1 引用了至少一个 evidence
+1 引用 doc_id 在检索结果中存在
+1 没有引用无权限文档
+1 回答包含延期原因
+1 回答包含上线影响
-1 出现 evidence 中没有的原因
-1 没有说明不确定性
```

最终 reward：

```text
reward = citation_score + groundedness_score + format_score + safety_score
```

GRPO 怎么用：

```text
回答 A：引用正确，原因正确，风险正确 -> reward 5
回答 B：原因正确，但没引用 -> reward 3
回答 C：引用旧文档，原因错 -> reward 1
回答 D：胡编 -> reward 0
```

GRPO 在这一组里计算相对 advantage，让模型更倾向生成 A 这种回答。

面试里可以这样说：

> 如果任务可以自动验证，比如引用是否存在、格式是否合法、工具参数是否正确，就可以构造 verifier reward，用 GRPO/RLVR 强化任务成功率。但如果任务需要专家主观判断，比如答案是否“更有帮助”，则更适合 DPO 或人工评估。

## 8. 模块六：数据合成系统怎么接入

线上 badcase 数量可能不够，所以要做数据合成。

从一个 badcase 合成多个训练样本：

```text
“A 项目为什么延期？”
“这次延期会不会影响正式上线？”
“本周 A 项目最大的风险是什么？”
“谁阻塞了 A 项目的灰度？”
“A 项目灰度时间有什么变化？”
```

也可以合成不同难度：

| 难度 | 样本 |
| --- | --- |
| easy | 证据里直接写延期原因 |
| medium | 多篇会议纪要，需要找最新一篇 |
| hard | 需要结合会议纪要和排期表判断上线风险 |

合成数据不能直接进训练集。

质检流程：

```text
LLM 生成样本
-> 规则过滤格式
-> 去重
-> evidence 检查
-> LLM judge 打分
-> 人工抽检
-> 小规模训练验证
```

技术选型：

- 去重：MinHash / SimHash / embedding similarity
- 质检：规则 + 小模型分类器 + LLM judge
- 存储：合成样本和生成 prompt 都要进版本库
- 抽检：高风险类别人工复核

## 9. 模块七：LLM / Agent 评估平台

训练前后必须评估，否则不知道是不是变好了。

评估集包括：

- 线上 badcase 固化
- 人工构造 golden cases
- 合成 hard cases
- 安全/权限 cases
- 格式 cases
- 工具调用 cases

文档问答指标：

| 指标 | 含义 |
| --- | --- |
| answer correctness | 答案是否正确 |
| faithfulness | 是否忠于 evidence |
| citation accuracy | 引用是否正确 |
| retrieval recall@k | 正确文档是否被召回 |
| format accuracy | 是否按格式输出 |
| unsafe rate | 是否泄露或越权 |
| latency | 延迟 |
| token cost | token 成本 |

Agent 任务指标：

| 指标 | 含义 |
| --- | --- |
| task success rate | 任务是否完成 |
| tool call accuracy | 工具选得对不对 |
| argument accuracy | 参数填得对不对 |
| step count | 用了多少步 |
| loop rate | 是否陷入循环 |
| recovery rate | 工具失败后能否恢复 |

评估平台数据流：

```text
选择模型版本
-> 选择 prompt / retriever / tool 版本
-> 选择 eval set
-> 批量运行
-> 自动规则打分
-> LLM judge 打分
-> 人工抽检
-> 输出对比报告
-> badcase 回流
```

关键是版本对齐：

```json
{
  "model_version": "docqa_sft_20260601",
  "prompt_version": "rag_prompt_v4",
  "retriever_version": "hybrid_rag_v3",
  "eval_set_version": "docqa_eval_20260601",
  "dataset_version": "sft_docqa_20260601"
}
```

没有版本号，评估结果无法解释。

## 10. 模块八：RAG / Graph RAG 怎么接入

很多 badcase 不是模型不会答，而是没拿到正确证据。

所以训练数据系统要和 RAG 评估联动。

如果错误是召回旧文档：

- query rewrite 加时间约束
- metadata filter 加 `created_at`
- reranker 增加时间新鲜度

如果错误是同名项目混淆：

- 加项目 ID
- 加空间 / tenant / owner 权限过滤
- 加 entity linking

如果错误是只召回局部片段：

- parent document retrieval
- doc card summary
- chunk 邻接扩展

如果问题需要多跳关系，可以建图：

```text
Project A --blocked_by--> Backend API Integration
Backend API Integration --depends_on--> Service B
Service B --owned_by--> Team X
Project A --delays--> Launch Milestone
```

查询时：

```text
query
-> seed entity: Project A
-> 1-2 hop expansion
-> 找到 blocker / dependency / milestone
-> 召回相关文档和 evidence
```

技术选型：

| 阶段 | 选型 |
| --- | --- |
| MVP | Milvus / Elasticsearch vector + PostgreSQL + JSON/SQLite graph + RRF |
| 中等规模 | Milvus / Vespa + BM25 + Neo4j/NebulaGraph + Celery/Kafka |
| 生产化 | 多租户权限、版本管理、tracing、灰度、成本监控、回滚 |

面试回答：

> 我不会把所有问题都交给 Graph RAG。事实定位优先 dense retrieval，多跳关系再用 graph expansion。最后用 RRF 或 reranker 融合，并且回答必须带 evidence。

## 11. 灰度上线和回滚

训练完不能直接全量上线。

上线流程：

```text
离线评估通过
-> shadow 模式跑线上流量但不返回用户
-> 小流量灰度 1%
-> 对比 badcase rate / latency / cost
-> 扩到 10%
-> 全量
```

如果指标变差：

```text
自动回滚到上一模型版本
保留失败 trace
分析是模型问题、retriever 问题还是 prompt 问题
```

要监控：

- badcase rate
- 点踩率
- citation missing rate
- unsafe rate
- latency p95
- token cost
- tool failure rate
- retrieval recall proxy

回滚不是只回滚模型，还可能回滚：

- prompt version
- retriever version
- dataset version
- tool schema version
- graph index version

## 12. 面试里怎么讲这个案例

如果面试官问：

> 线上 badcase 怎么回流提升模型？

可以这样答：

> 我不会直接把线上 badcase 全部丢进训练集。首先会记录完整 trace，包括 query、answer、retrieved docs、tool calls、prompt version、model version 和 user feedback。然后对 badcase 做脱敏、去重和错误归因，判断它是检索问题、推理问题、格式问题还是安全问题。
>
> 如果是检索问题，优先修 query rewrite、metadata filter、reranker 或 Graph RAG；如果是回答格式和证据使用问题，可以构造 SFT 数据；如果是两个答案都合理但用户更偏好其中一个，可以构造 DPO chosen/rejected；如果有自动 verifier，比如引用是否存在、JSON 是否合法、工具参数是否正确，可以考虑 RLVR/GRPO。
>
> 最后这些数据不会直接上线，而是先进入版本化数据集，经过离线评估、LLM judge、人工抽检，再做小流量灰度。所有模型、prompt、retriever、数据集都要有版本号，方便效果变差时回滚。

这段就比较像真的做过系统，而不是背概念。

# 十四、面试时不要犯的错

## 1. 不要一上来堆技术

不要这样：

> 我会用 Kafka、Redis、K8s、Neo4j、Milvus。

先讲需求和数据流，再讲为什么需要这些技术。

## 2. 不要过度设计

100 篇论文没有必要一上来上复杂图数据库。

面试官更喜欢听：

> 当前规模下我会先做轻量版本，验证价值；后续规模上来再替换存储层。

## 3. 不要只讲功能，不讲指标

系统设计必须讲非功能指标：

- 延迟
- 吞吐
- 成本
- 安全
- 可回滚
- 可观测

## 4. 不要说“这个方案最好”

要说：

> 在当前约束下，这个方案更合适。

工程设计没有绝对最好，只有适合约束。

# 十五、最后速记

面试前只要记这张表：

| 问题 | 回答关键词 |
| --- | --- |
| 如何从需求到设计 | 澄清需求 -> 拆模块 -> 画数据流 -> 定指标 |
| 如何比较方案 | 正确性、复杂度、成本、延迟、吞吐、安全、扩展 |
| 如何应对限制 | 先 MVP，再按瓶颈演进 |
| 如何提升扩展性 | 模块化、稳定 schema、配置化、异步解耦、版本管理 |
| 飞书岗位怎么贴 | 训练数据 pipeline、数据合成、评估平台、数据飞轮 |

一句话：

> 软件工程不是背概念，而是在资源有限的情况下，把一个模糊需求拆成一个能跑、能改、能扩、能定位问题的系统。
